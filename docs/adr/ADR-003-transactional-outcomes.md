# ADR-003 — Transactional commands and exactly-once outcomes

Status: implementation contract proposed under M1-T01; dependency gate pending. Date: 2026-09-30.

Context: Repeated input, animation callbacks, and reload can accidentally repeat a reward or charge.

Decision: One Application command gate evaluates an isolated candidate, validates it, durably commits state plus receipt/consumed activity/cues, then publishes. Command IDs bind canonical payloads. Simulation operation IDs and planned activity IDs prevent repeating automatic work under another command ID. Retry returns the original receipt; mismatched payload rejects. Failures before commit preserve all state, including RNG and revision.

Consequence: Presentation renders outcomes and cannot grant rewards. Persist every authoritative boundary initially. Ambiguous post-replace I/O failure enters RecoveryRequired, blocks fresh commands, and reconciles the stored generation before answering. Multi-boundary advance returns explicit committed progress and stop reason. Retain receipts for MVP; pruning needs a later audited compaction contract.

Verification required: duplicate request, fresh-ID replay of consumed activity, animation replay, save/reload retry, and fault injection before/after replacement. See [contracts](../architecture/FIRST_PLAYABLE_CONTRACTS.md). No durability or exactly-once runtime result is claimed yet.

Historical batch identity compatibility (PR #7 follow-up): pre-PR6 `root/index` and PR6 `$batch/{length}:{root}/index` can encode identical bytes for different caller roots. An `abc` PR6 batch and a pre-PR6 `$batch/3:abc` batch are indistinguishable in schema 1. Neither the retry caller, current revision, receipt payload nor date proves ownership. Sessions with unresolved ownership allow snapshots/checkpoint export but block commands with `RecoveryRequired` / `save.batch_owner_required` and batches with `RecoveryRequired`; no store commit occurs. A raw-root alternative exceeding the historical 256-character caller limit is impossible and needs no binding.

An importer with trusted provenance may supply `GameSession`'s optional `legacyBatchOwners` dictionary. Each key is the exact ambiguous persisted child prefix (for example `$batch/3:abc/`) and each value is its known caller root (`abc` for PR6, `$batch/3:abc` for pre-PR6). Bindings are validated and copied. Do not derive them from the incoming command or guess a default format. Provenance must cover each ambiguous group; saves without it require external recovery, not automatic reassignment.

New children start with 257 dollar signs followed by `batch/{length}:{root}/index`. Historical callers and pre-PR6 children were limited to 256 characters; PR6 children always began `$batch/`. These namespaces are disjoint even when a PR6 generated ID exceeded 256 characters.

The supported restore/import entry point is `GameSession.TryRestore(catalog, serializer, store, out session, out load, owners)`. `Recover(owners)` supports an existing session. Both durably normalize historical child IDs before returning a ready session. The constructor path applies the same recovery gate before answering a command/batch, including a completed retry. An importer supplies trusted ownership once; subsequent fresh-process restores read ownership directly from the normalized IDs without another binding or gameplay command. Unknown provenance reports `LoadStatus.RecoveryRequired` / `save.batch_owner_required` and returns no ready session. A store without the recovery-write capability reports `save.compatibility_store_required`.

`ISaveCompatibilityStore.CommitReceiptCompatibility` is a dedicated same-revision recovery operation. It compares the entire expected checkpoint under the normal writer lock, allows only historical batch-child ID replacements, and rejects changes to any other state or receipt field. It writes/flushes/validates/replaces and reads back before publishing. Successful recovery also places the normalized checkpoint in backup at the same logical generation, so ownership survives backup recovery. Normal gameplay commits still require revision +1. Failure before replacement preserves the original; possible replacement enters RecoveryRequired and reconciles storage. The recovery operation grants no reward, advances no time, allocates no operation, and changes no RNG/ledger/salary. A completed retry then only replays original operation IDs, revisions and minutes. Schema 1 and its existing migration remain unchanged; historical day/month fixtures, fresh-process restore, backup recovery, competing ownership resolutions and fault injection cover this receipt-ID compatibility transform.

If an interrupted recovery promoted primary before mirroring backup, a read-only store read identifies that exact pair: same generation, every other state/receipt field identical, and each changed ID a valid historical-to-internal replacement. It reports `save.receipt_compatibility_pending` with the valid primary. The restore gate completes the dedicated recovery write before returning a ready session, using ownership already committed in primary; a cold process needs no transient binding. Different-generation or different-gameplay checkpoints never qualify for this repair.
